# OpenAI Integration

## Decision

This prototype uses the official **Codex App Server** supplied by the user's installed ChatGPT/Codex tooling. The overlay launches its own `codex app-server` child process and communicates with that process over the default newline-delimited JSON protocol on standard input and output.

This is deliberately different from attaching to the running ChatGPT desktop GUI. The desktop application's private processes, pipes, sockets, authentication state, and internal `chatgpt.com` endpoints are not a public integration contract. The prototype must not discover, inspect, or connect to them. OpenAI documents Codex App Server—not a general-purpose “ChatGPT app server”—as the interface for custom rich Codex clients.

The official overview describes App Server as the interface for embedding Codex authentication, conversation history, approvals, and streamed agent events in another product: [Codex App Server](https://learn.chatgpt.com/docs/app-server).

## Prototype architecture

The overlay treats the installed Codex runtime as a local dependency:

1. Resolve a `codex` executable from the installed tooling.
2. Spawn `codex app-server` as a child process. No network listener is needed for the prototype because standard input/output is the default transport.
3. Write one JSON request or notification per line to the child's standard input.
4. Parse one JSON response or notification per line from standard output. Keep standard error separate for diagnostics so log text can never corrupt the protocol stream.
5. Shut down the child process when the overlay exits. If it terminates unexpectedly, report that the local Codex service stopped; the UI's **Retry** action starts a fresh child process.

App Server also documents WebSocket and Unix-socket transports, but the WebSocket transport is explicitly experimental. Standard input/output keeps the prototype local, avoids opening a port, and gives the overlay ownership of the exact server instance it talks to.

## Authentication

Authentication is owned by Codex App Server. The overlay must not read the ChatGPT desktop application's cookies, token files, Keychain entries, or private session data.

The expected flow is:

1. After protocol initialization, call `account/read` to inspect the current App Server account state.
2. If a managed ChatGPT account is already available, continue without copying credentials into the overlay.
3. Otherwise call `account/login/start` with `type: "chatgpt"`. Open the returned `authUrl` in the user's browser and wait for `account/login/completed` followed by `account/updated`.
4. Device-code login (`type: "chatgptDeviceCode"`) is a documented fallback when a browser callback is unsuitable.
5. App Server owns token persistence and refresh for managed ChatGPT authentication. The overlay stores no ChatGPT access or refresh token.
6. API-key authentication is a separate supported App Server mode, but it is not the prototype's default. It uses OpenAI Platform billing rather than included ChatGPT plan access.

The exact account methods and managed browser/device-code flows are documented under [App Server auth endpoints](https://learn.chatgpt.com/docs/app-server#auth-endpoints). OpenAI's [authentication guidance](https://learn.chatgpt.com/docs/auth#openai-authentication) distinguishes ChatGPT subscription access from API-key, usage-based access.

## Protocol lifecycle

App Server uses bidirectional JSON-RPC-style messages with the normal `"jsonrpc": "2.0"` field omitted on the wire. Requests contain `method`, `params`, and `id`; responses echo `id`; notifications omit `id`.

For each child-process connection, the overlay follows this lifecycle:

1. Send exactly one `initialize` request with stable `clientInfo` identifying this overlay.
2. After the response, send the `initialized` notification. No other method may run before this handshake.
3. Complete the account check/login flow described above.
4. Call `thread/start` for a new ephemeral conversation, explicitly pinning
   `gpt-5.6-luna`, medium reasoning effort, and concise reasoning summaries.
   The thread uses the user's persisted operating folder when selected, or a
   neutral private application-support directory otherwise. It always uses a
   read-only sandbox and `never` approval policy. Changing or removing the
   operating folder replaces the thread so one thread never spans two folders.
5. For each submitted message, call `turn/start` with the thread ID and an input
   array. Text uses `{ "type": "text", "text": "..." }`; each pending private
   screenshot uses `{ "type": "localImage", "path": "/absolute/path.png" }`,
   matching the schema generated by the installed App Server. Each turn
   reasserts the pinned model, medium effort, concise summary, and same working
   directory as its thread.
6. Keep reading asynchronous notifications. Before final answer text arrives,
   display safe progress derived from documented commentary, reasoning-summary,
   plan, and generic tool lifecycle events. Never display raw reasoning text,
   commands, arguments, or tool output. Append `item/agentMessage/delta` final
   answer text to the Markdown view, finalize items on `item/completed`, and
   mark the request finished only on `turn/completed`.
7. Use `turn/interrupt` when the user cancels generation.
8. Reject unsupported server-initiated requests with a JSON-RPC error; never silently approve filesystem, command, network, or other consequential actions merely because the UI is compact.

Atmosphere launches App Server with an isolated Codex home at
`~/.atmosphere/codex-home` and shares only the user's private ChatGPT
authentication file. App Server config maps deep-merge, so an empty
`mcp_servers` override alone would not remove servers configured in the normal
Codex home. The separate home prevents Atmosphere from inheriting MCP servers,
plugins, hooks, or project-trust configuration at all. Process and per-thread
configuration additionally disable Computer Use, code mode, browser control,
web search, connected apps, plugins, and subagents. This keeps the overlay
single-agent and prevents an answer from moving the pointer or opening a
control surface. The built-in shell remains available only inside the read-only
sandbox for relevant operating-folder inspection, and login-shell semantics
are disabled.

The prototype stays on the non-experimental surface by setting `experimentalApi` to `false`. Protocol concepts, message shapes, lifecycle, and event names are documented in [Codex App Server](https://learn.chatgpt.com/docs/app-server).

## Compatibility limitations and future hardening

App Server evolves with the installed Codex version. OpenAI states that generated TypeScript and JSON Schema artifacts are specific to the Codex version that produced them. The CLI reference also cautions that the `codex app-server` command is primarily intended for development and debugging and may change without notice.

The current prototype relies on the installed App Server accepting the methods
and shapes it uses. It does not yet preflight the Codex version, pin generated
schemas, or call `model/list`. Unknown notification methods are ignored, while
request failures and malformed JSON are surfaced to the UI as errors.

Before distributing the overlay broadly, it should:

- check the installed Codex version before launch and provide a clear unsupported-version error;
- pin and test a supported version range rather than relying on undocumented behavior;
- generate or vendor schemas from that supported version using `codex app-server generate-json-schema` or `generate-ts`;
- ignore unknown notification fields and methods where safe, while treating malformed required fields as protocol errors;
- fail gracefully on `method not found` and avoid all experimental methods; and
- keep App Server integration behind a provider boundary so it can be replaced without rewriting the overlay UI.

See the [Codex App Server schema guidance](https://learn.chatgpt.com/docs/app-server#message-schema) and [`codex app-server` command reference](https://learn.chatgpt.com/docs/developer-commands#codex-app-server).

## Why the production alternative is the Responses API

Codex App Server is a pragmatic prototype choice because it provides a documented local client protocol and can use managed ChatGPT sign-in without embedding an OpenAI API key. Its tradeoffs are an installed-runtime dependency, Codex-specific behavior, local process management, and a version-coupled protocol.

For a distributed, general-purpose assistant, the production architecture should instead be:

```text
macOS overlay -> product backend -> OpenAI Responses API
```

OpenAI recommends the Responses API for new projects. It provides direct model requests, tools, multi-turn state, and streaming without coupling the client to a locally installed Codex build. A production backend can use the Conversations API or `previous_response_id` for state and stream response events to the overlay.

The backend boundary is important: OpenAI says API keys are secrets and must not be exposed in client-side applications. Ordinary Responses API usage is billed through the OpenAI Platform; a consumer ChatGPT subscription is not a general API credential.

Official references:

- [Migrate to the Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses)
- [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)
- [Streaming API responses](https://developers.openai.com/api/docs/guides/streaming-responses)
- [OpenAI API authentication](https://developers.openai.com/api/reference/overview#authentication)

## Non-goals and prohibited shortcuts

This integration does not:

- attach to a server process owned by the running ChatGPT GUI;
- scan for private Unix sockets, XPC services, named pipes, or loopback ports;
- read or reuse the desktop application's private authentication cache;
- call undocumented ChatGPT web or `backend-api` endpoints;
- automate the ChatGPT GUI to submit prompts; or
- treat Apps SDK/MCP plugins as an inference API. Those systems let ChatGPT or Codex call tools exposed by another service; they do not provide a native overlay with a ChatGPT response channel.

These boundaries keep the prototype on documented OpenAI interfaces and make the future migration to the Responses API straightforward.
